# Задача — `spec/sql`: компактный заголовок `@odts 0.1` (фронтенд → YAML `@bruin`)

**Статус:** 📋 запланировано · **Приоритет:** средний · **Рекомендуемая модель:** Opus 4.8 @ `high`

Lane: `spec`. Область: `spec/`, `src/ogip/spec_compile/`. Issue: [#35](https://github.com/dataengy/ogip/issues/35).
Решение зафиксировано в [ADR-0016](../../docs/adr/ADR-0016-odts-authoring-format-spec-sql.md); рабочие
правила — в [spec/sql/AGENTS.md](../../spec/sql/AGENTS.md).

## Цель

Заменить многословный YAML-заголовок `@bruin` компактным строчно-ориентированным заголовком `@odts 0.1`,
**не трогая адаптеры**: фронтенд рендерит `@odts` → текст YAML `@bruin`, а существующий
конвейер `parse_asset()` продолжает работать без изменений.

```
spec/sql/**/*.sql (@odts, SSoT) ──▶ rendered @bruin YAML ──▶ parse_asset() ──▶ adapters
```

Выполнять **после** [spec-macros.md](spec-macros.md) — та задача закрепляет синтаксис макросов
внутри тела, эта — заголовок вокруг него.

## Почему текст YAML, а не сразу `Asset`

`to_bruin` копирует файлы ассетов **дословно**, поэтому таргету Bruin в любом случае нужен настоящий
текст заголовка `@bruin`. Его рендеринг требуется существующим таргетом; пропуск промежуточного
шага ничего бы не дал и лишь скрыл бы этап.

## Согласование словаря с OTS (существующие наработки — оценены)

[OTS](https://github.com/francescomucio/open-transformation-specification) был проанализирован:
**[docs/comparisons/ots-vs-odts.md](../../docs/comparisons/ots-vs-odts.md)**. Это формат
*обмена*, а не авторинга, поэтому он не принят — но он уже даёт имена вещам, которые понадобятся
`@odts`, и совпадение имён сейчас бесплатно, а беспричинное расхождение позже обойдётся дорого.

- [ ] Когда материализация выйдет за пределы `table`/`view`, использовать имена из OTS: `incremental` с
      `delete_insert` / `append` / `merge` и `scd2` с `start_column` / `end_column` /
      `unique_key`, плюс `on_schema_change`. Не выдумывать синонимы.
- [ ] Словарь `checks:` — уровень колонок vs уровень таблицы, а также `severity: error|warning`.
- [ ] Рассмотреть `object_tags` (governance-теги, переносимые на объект хранилища: PII,
      классификация) как отдельные от `tags` (выборка/обнаружение). Для 0.1 не нужно; зафиксировать
      до того, как `pii` перерастёт атрибут колонки.

**Не зависеть от OTS** — версия до 1.0, один мейнтейнер, ломающие изменения между 0.1 → 0.2.2.
Согласование словаря обратимо; зависимость от формата — нет.

## Набросок

- [ ] Парсер заголовка `@odts 0.1` — рекурсивный спуск, одна директива на строку
      (`model` · `kind` · `owner` · `tags` · `depends` · `columns` · `checks` · `imports`),
      плюс блок атрибутов колонок с отступами.
- [ ] Рендерер → YAML `@bruin`; **round-trip-тест** по каждой текущей модели, чтобы
      сгенерированный YAML был доказуемо эквивалентен сегодняшнему рукописному заголовку.
- [ ] Диспетчеризация по маркеру в `parse_asset()`: `/* @odts` → фронтенд, `/* @bruin` → легаси-путь.
      Во время миграции валидны оба.
- [ ] **Вывод, а не авторинг**: убрать `type: duckdb.sql` (выводится автоматически). Сделать `depends`
      необязательным — выводить через `dialect.table_refs()`, а если он написан, трактовать как
      утверждение: **валить компиляцию, если он расходится с AST**.
- [ ] Десахаризация LValue: переписывать `PropertyEQ` → проекцию с алиасом, **только** как прямого
      потомка списка проекций. Вложенный `:=` — это именованный аргумент DuckDB, его не трогать.
      Отклонять `EQ` в проекции с понятной ошибкой, указывающей на `:=`.
- [ ] Сконвертировать четыре существующие модели; отрендеренный YAML **никогда не коммитится**.
- [ ] Синхронизация документации — см. ниже. Десять документов утверждают формат независимо друг от друга.

## Целевая форма

16 строк заголовка → 8, при этом `type` и `depends` выводятся автоматически:

```
/* @odts 0.1
model     core.game
kind      table
owner     data-eng@ogip
tags      core, entity, daily

columns:
  game_sk   varchar   pk !null unique
  title     varchar   !null
*/
```

## Проверять запуском, а не предположениями

Предположения о поведении sqlglot/sqlfluff/DuckDB в этом дизайне уже дважды оказывались неверными
— оба раза в духе «парсится — значит работает». Проверяйте поведение на закреплённых версиях
(sqlglot 30.8.0 · DuckDB 1.5.4 · sqlfluff 4.2.2), а не рассуждайте о нём.

## Критерии приёмки

- Все модели в `spec/sql` написаны как `@odts 0.1`; закоммиченных YAML-дубликатов нет.
- Round-trip-тест доказывает: отрендеренный YAML ≡ прежним рукописным заголовкам.
- `depends`, противоречащий AST SQL, валит компиляцию.
- `select x = y` в проекции отклоняется с понятной ошибкой; `select x := y` работает.
- `just spec-compile all` · `just spec-verify` · `just sql-lint` · `make check` зелёные.
