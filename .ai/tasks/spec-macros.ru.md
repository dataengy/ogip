# Задача — `spec/sql`: слой макросов `@odts` (реестр + нативные адаптеры под каждый движок)

**Статус:** 📋 запланировано · **Приоритет:** средний · **Рекомендуемая модель:** Sonnet 5 @ `high`

Lane: `spec`. Область: `spec/`, `src/ogip/spec_compile/`. Issue: [#36](https://github.com/dataengy/ogip/issues/36).
Решение зафиксировано в [ADR-0016](../../docs/adr/ADR-0016-odts-authoring-format-spec-sql.md); рабочие
правила — в [spec/sql/AGENTS.md](../../spec/sql/AGENTS.md).

## Цель

Дать `spec/sql` семантические макросы — `@ns.name(args)` — определяемые один раз и компилируемые
**нативно под каждый движок**, чтобы использовалась собственная макросистема продакшен-движка,
а не обходилась стороной.

## Почему это первым

Меньше по объёму, чем компактный заголовок, и точки вызова уже существуют: `core/game.sql` вручную пишет
`md5(cast(game_id as varchar))` и `extract(year from released_date)`.

## Набросок

- [ ] Реестр — одно определение макроса, несущее семантику + рендеринг под каждый таргет. Начать
      **ровно с двух**: `@keys.hash`, `@dates.year`. Никакой библиотеки впрок, до реального спроса.
- [ ] Фронтенд: распознавать `@ns.name(...)` в теле SQL; разрешать `imports:` (без глобалов).
- [ ] Адаптеры:
      - `to_sqlmesh` → эмитить `@DEF(...)` из реестра, точки вызова оставлять как `@`
      - `to_dbt` / `to_sqlmesh_dbt` / `to_bruin` → Jinja
      - раннер plain-SQL → разворачивать в нативный SQL
- [ ] **Тест соответствия** (смысл всей задачи, см. ниже).
- [ ] Сконвертировать две точки вызова в `core/game.sql`; `just spec-verify` остаётся зелёным.
- [ ] Задокументировать реестр в [spec/README.md](../../spec/README.md).

## Существующие наработки согласны с дизайном — и останавливаются на шаг раньше

[OTS](https://github.com/francescomucio/open-transformation-specification) независимо пришёл к той же
форме: его `functions` несут `code.generic_sql` **плюс** `code.database_specific` с ключом по базе
данных — одно семантическое определение, рендеринги под каждый движок, ровно тот реестр, что ниже
([полный разбор](../../docs/comparisons/ots-vs-odts.md)).

Он **не** описывает, как рендеринги удерживаются в согласии между собой. Этот пробел и закрывает тест
соответствия — а значит, это та часть задачи, где не на что опереться из существующих наработок, и та,
которую вероятнее всего срежут под давлением сроков. Не срезать.

## Тест соответствия — не обсуждается

Компиляция одного макроса в четыре нативные реализации — это четыре шанса разойтись, и сбой
при этом тихий: `dbt_utils.generate_surrogate_key` хэширует **не** так, как
`md5(cast(x as varchar))`, поэтому одна и та же модель получала бы разные ключи в зависимости от
профиля запуска — инцидент с данными, который обнаружат далеко ниже по потоку, если вообще обнаружат.

Сам тест: для каждого макроса — одна фикстурная таблица, прогоняемая через **каждый** адаптер на DuckDB,
с проверкой побайтово идентичного результата. Макрос без зелёного теста соответствия не приземляется.

## Критерии приёмки

- `@keys.hash` / `@dates.year` используются в `spec/sql`, разрешаются через `imports:`.
- `just spec-compile all` зелёный; вывод SQLMesh содержит настоящие `@DEF` + точки вызова `@`.
- Тест соответствия существует и зелен для обоих макросов; намеренная поломка рендеринга одного
  адаптера делает его красным.
- `make check` + `just sql-lint` + `just spec-verify` зелёные.
