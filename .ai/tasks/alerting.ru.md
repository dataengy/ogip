# Задача — Единый алертинг: Notifier + Telegram/Mattermost/Slack (Фаза 7)

**Статус:** 🚧 в работе — абстракция + три транспорта отгружены, покрыты юнит-тестами и
проверены против живого Telegram API. Конфиг пока env-driven (секция SSoT — это handoff);
ни один источник алертов ещё не подключён.

Lane: `alerting` (объект блокировки для параллельных сессий). Объём: `src/ogip/alerting/`,
`src/tests/unit/test_alerting.py`. Issue: [#11](https://github.com/dataengy/ogip/issues/11).
Часть **Фазы 7 — Наблюдаемость** ([PLAN](../PLAN.md) A10) вместе с обс-стеком
([observability.md](../../docs/architecture/observability.md)).

## Зачем

PLAN A10 требует протокол `Notifier` — абстракцию алертов, чтобы бизнес-код говорил, *что*
произошло, и никогда не знал, *куда* это уходит. Обс-стек (VictoriaMetrics/Loki/Grafana)
отвечает на вопрос «что происходит»; алертинг — на «кому-то нужно узнать прямо сейчас».

## Сделано

- `base.py` — протокол `Messenger` (как доставить), `Notifier` (доставлять ли/что: dry-run,
  fallback, **никогда не бросает исключений**), `NotifyResult`, `split_message`.
- `telegram.py` · `mattermost.py` · `slack.py` — три транспорта, каждый со своим health-check.
- `settings.py` — маршрутизация `OGIP_ALERT_*` + креды `OGIP_TG_*` / `OGIP_MM_*` / `OGIP_SLACK_*`.
- `__init__.py` — `make_notifier()`; возвращает `None`, когда ничего не сконфигурировано, так что
  пайплайн без кредов остаётся зелёным и просто молчит.
- 23 юнит-теста (httpx замокан через respx), с мутационной проверкой.

## Заметки по дизайну

- **Алерт не должен становиться вторым отказом.** `notify()` возвращает результат и никогда не
  бросает исключений.
- **Доставка через fallback — всё равно деградация.** Она сообщает `sent=True` с именем
  *fallback'а* и причиной, называющей отказавший primary, — алерт выживает, проблема остаётся видимой.
- **Без ретраев.** Отказавший primary сразу падает на fallback, вместо того чтобы парковать и
  без того несчастный пайплайн за бэкоффом.
- **Ловушка Slack**: `chat.postMessage` отвечает `HTTP 200` с `{"ok": false}` при ошибке.
  Обработка только по статус-коду молча глотала бы каждый такой алерт, поэтому `ok` проверяется
  и по нему поднимается ошибка.
- Архитектура адаптирована из зрелого приватного мониторингового стека; код — clean-room: в
  этом публичном репозитории нет корпоративных id тикетов, имён хостов или ботов.

## Проверено

- `ruff` · `pyright --strict` · pytest 23/23 зелёные.
- **Живой Telegram** (не моки): health-check `getMe`, реальная доставка, сообщение на 5464
  символа, разбитое и доставленное двумя постами, и намеренно сломанный primary, деградирующий
  на fallback.
- Мутационная проверка: удаление slack-гарда `ok` или лимита разбиения делает сьют красным.

## Блокировано / handoff

→ lane `core-pipeline` (владеет `config/`): перенести маршрутизацию в `config/config.yml`
`alerting:` + отразить её в `config/.env-render.py` (включая слоты секретов), затем заменить
литеральные дефолты в `settings.py` на `_yaml("alerting", …)`. Подробности: [STATUS.md](../STATUS.md).
