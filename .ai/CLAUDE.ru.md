# OGIP — инструкции проекта (Claude Code)

**OGIP (Open Games Intelligence Platform)** — production-уровня OSS-платформа **Market
Intelligence** для игровой индустрии; продукт = **ML-ready Parquet-датасеты** для DS/ML/аналитиков.
Витрина портфолио-качества для навыков Senior/Staff Data Engineer. Преемник OGAP
(`../Hushcrasher/`), намеренно проще.

**Основные правила живут в [AGENTS.md](AGENTS.md)** (тот же каталог) — общие правила, принцип
«production-путь священен», закон именования слоёв, SSoT `spec/` (Bruin + ODCS),
SSoT-конфигурация, планка качества, профили запуска. Этот файл добавляет только заметки о
рабочем процессе, специфичные для Claude.

## Рабочий процесс

- Поэтапная поставка с **гейтами одобрения пользователя** после каждой фазы
  (план: [PLAN.md](PLAN.md) · статус: [STATUS.md](STATUS.md) · задачи: [tasks/](tasks/)).
- После каждой фазы: объяснить решения, показать дерево, спросить одобрение перед продолжением.
- Пакетная/разовая работа идёт через скрипты в `.tmp/` (`.tmp/.once/` — для одноразовых);
  долговечные интерфейсы уходят в Makefile/Justfile + документацию.
- Коммиты по конвенциям /smart-commit: Conventional Commits, с разбивкой по категориям
  (chore(ai)/docs/ci/feat/test).
- **Push без спроса** — постоянная авторизация, без гейта на каждый push. Предусловия — все
  сразу, каждый раз:
  1. `make check` (или CI-эквивалентное подмножество) **зелёный локально** для файлов, которыми
     вы владеете.
  2. Вы пушите **только коммиты своего lane** — параллельные сессии делят эту ветку, поэтому
     `git log origin/<branch>..HEAD` не должен содержать ничего, что написали не вы. Никогда не
     пушьте работу чужого lane, тем более красную, чтобы приземлить свою.
  3. Каждый коммит несёт `Refs: #<issue>` / `Closes: #<issue>` (принуждается
     `.ci/steps/commit-binding.sh`).
  4. **Никогда не делайте force-push** в общую ветку (`main`, `dev`) — сюда коммитят 4+ агентских
     сессий, и перезапись истории уничтожает их незавершённую работу. Без исключений.
- Ветки: работа приземляется в **`dev`**; `dev → main` идёт через **PR** с зелёным CI
  (`.github/workflows/ci.yml` уже запускается на `pull_request`). `main` остаётся релизопригодной.
- **Политика merge PR (#57)** — принудительно закреплена настройками репозитория с 2026-08-20; SSoT
  `~/.ai/skills/.settings/branch_rules.yml#pr_merge`; merge через `just gh-merge-as <pr>`
  (флаги политики — его значения по умолчанию):
  - Каждый merge PR — **squash**, единственный метод, который разрешает репозиторий.
  - Слитые head-ветки **удаляются** (auto-delete репозитория), кроме долгоживущих:
    `main`, `dev`, `ru-docs` защищены (без удаления, без force-push).
  - После squash-релиза `dev → main` в `dev` делается **back-merge `origin/main`** — squash
    разрывает родословную, и следующий релизный PR переиграл бы всю историю (`gh-merge-as`
    печатает рецепт).
  - **`ru-docs` освобождена от всего этого** (#55): она никогда не создаёт PR и никогда не мержится.

## Скиллы

Прежде чем тянуться к каталожному скиллу, прочитайте **[SKILLS.md](SKILLS.md)**. Общий каталог
построен в основном под GitLab + Jira + ClickHouse; ~193 из его 521 скилла нацелены на
инфраструктуру, которой у OGIP нет, и отказывают они *беззвучно* — корректно оформленная
Jira-задача для проекта без Jira. `SKILLS.md` перечисляет, что здесь используется (с файловыми
свидетельствами), что подходит стеку и что не трогать.

## Команды (целевые — созданы в Phase 0)

- Гейты: `make check` (= ruff + pyright strict + pytest); паритет с CI: `make ci`
- Запуск: `make run` (полный пайплайн на сэмпл-данных); `just run-profile <name>` (профили A12)
- Инфраструктура: `make up` / `make obs-up` / `make down` (compose: `deploy/docker-compose.yml`, env: отрендеренный `.env`)
- Конфигурация: правьте `config/config.yml` → `make render-env` (никогда не правьте производные значения `.env`)
- Runtime-окружение: `UV_PROJECT_ENVIRONMENT=.run/venv` (экспортируется всеми build-файлами)

## Ключевые пути

`docs/` · `.run/` (runtime, в gitignore).
