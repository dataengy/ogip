# Конформанс-примеры ODTS 0.1

Шесть из шестнадцати живых моделей `spec/sql`, переоформленные с заголовками `@odts 0.1` — та
же раскладка (`<layer>/<name>.sql`), те же SQL-тела **байт в байт**, отличается только заголовок.
`just standards-validate` утверждает всё это: закрытый словарь директив, согласие имени модели
с путём, идентичность тела с соответствующим файлом `spec/sql` и эквивалентность
инлайн-атрибутов проверок фикстуры проверкам `@bruin` этой модели — поэтому эти фикстуры не
могут молча разойтись с SSoT, который они описывают, ни в SQL, ни в контракте.

Это примеры стандарта, а не SSoT: живые файлы `spec/sql` сохраняют легаси-заголовки `@bruin`,
пока не приземлится фронтенд `@odts`
([#35](https://github.com/dataengy/ogip/issues/35)); во время миграции валидны оба маркера.

Что показывает конвертация — по правилу вывода профиля (SPEC.md §4):

- `type: duckdb.sql` исчез — выводится из авторского диалекта и расширения файла;
- `depends:` исчез — выводится из SQL AST (`raw.rawg__games` → `staging.stg_games` →
  `core.game` → `fs.market_features`, и `raw.metacritic__game` →
  `staging.stg_metacritic_games`); писать его можно только как проверяемое утверждение;
- колоночные списки `checks:` из `@bruin` схлопываются в инлайн-атрибуты (`!null`, `unique`,
  `non_negative`);
- у свободнотекстового `description:` модели `raw` нет директивы в 0.1 — директива `doc`
  отложена (SPEC.md §10);
- вызовы макросов (`@keys.hash(game_id)` для суррогатного ключа `core.game`) станут
  каноническими только с приземлением реестра макросов
  ([#36](https://github.com/dataengy/ogip/issues/36)); до тех пор тела остаются идентичными
  живому SQL.
