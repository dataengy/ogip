# Нормативный профиль ODTS 0.1

**Статус:** утверждённый профиль OGIP
**Версия:** 0.1
**Область действия:** формат авторинга `@odts` для `spec/sql`, компилируемый в шесть целей OGIP
(SQLMesh · dbt · OpenDBT · SQLMesh-over-dbt · Bruin · plain SQL)

Ключевые слова **MUST** («обязано»), **MUST NOT** («обязано не»), **SHOULD** («следует») и
**MAY** («может») нормативны. Источники авторитета: [руководящий бриф](GOVERNING-BRIEF.md)
(принципы дизайна), [ADR-0016](../../docs/adr/ADR-0016-odts-authoring-format-spec-sql.md)
(принятая политика) и [`spec/sql/AGENTS.md`](../../spec/sql/AGENTS.md) (рабочие правила). Там,
где бриф говорит с позиции 0.2, этот профиль берёт подмножество 0.1; §10 перечисляет
отложенное.

## 1. Граница

ODTS описывает аналитические преобразования: что вычисляет модель, её колонки и её ограничения
корректности. Он описывает **намерение**; реализацией владеют адаптеры компилятора.

- Оркестрация — расписания, ретраи, триггеры, порядок выполнения — принадлежит
  [ODOS](../ODOS/SPEC.md) и MUST NOT появляться в ODTS-документе.
- Статистический мониторинг (свежесть, объём, аномалии, дрейф схемы) — это наблюдаемость, а не
  корректность, и находится вне документов 0.1 (им владеет `dq/`).
- Контракты обмена датасетами принадлежат ODCS (`spec/contracts/`).
- Термины движков и вендоров (`MergeTree`, `Delta`, `Iceberg`, имена движков) MUST NOT
  появляться в переносимом документе. Движко-специфичный SQL живёт только в `_ext/<engine>/`.

## 2. Документы и версионирование

ODTS-документ — это один SQL-файл: комментарий-заголовок, за которым следует ровно один
SQL-оператор.

```
/* @odts 0.1
model     core.game
kind      table
owner     data-eng@ogip
tags      core, entity, daily

columns:
  game_sk   varchar   pk !null unique
  title     varchar   !null
*/
select ...
```

- Первая строка заголовка MUST быть `@odts <version>`. Версия применяется ко всему файлу;
  блоки MUST NOT нести независимые версии (по ADR-0016 — отклонено, а не просто отложено).
- Один документ определяет одну модель. Имя модели SHOULD совпадать с
  `<parent-directory>.<file-stem>` пути документа.
- Документы пишутся на авторском диалекте профиля (DuckDB для OGIP, объявляется один раз в
  конфигурации проекта — `SPEC_DIALECT`), никогда не пофайлово.

## 3. Грамматика заголовка

Заголовок строчно-ориентирован: одна директива на строку, имя и значение разделены пробельными
символами. Выравнивание косметично и MUST NOT нести смысл. Вложенный YAML MUST NOT
использоваться.

Словарь директив 0.1 закрыт:

| Директива | Форма | Статус |
|---|---|---|
| `model` | `model  <layer>.<name>` | обязательная |
| `kind` | `kind  table \| view` | обязательная |
| `owner` | `owner  <owner-id>` | необязательная |
| `tags` | `tags  a, b, c` (через запятую) | необязательная |
| `depends` | `depends  <model> [, <model>…]` | необязательная — только утверждение (§4) |
| `columns:` | блок (§5) | необязательная |
| `checks:` | блок (§6) | необязательная |
| `imports:` | блок (§7) | необязательная |

Неизвестная директива MUST приводить к ошибке компиляции. Сквозной передачи нет: директива,
которую адаптер проигнорировал бы, — утечка переносимости; то же правило закрытого словаря, что
и в ODOS.

Семантическая классификация (entity · fact · dimension · history · snapshot · feature) в 0.1
переносится в `tags`; выделенная директива `type` отложена (§10).

## 4. Вывод прежде авторинга

Директива, которую можно вычислить, MUST NOT быть обязательной, а будучи всё же написанной, она
становится утверждением, которое компилятор проверяет:

- **Тип движка/файла** (`type: duckdb.sql` эпохи `@bruin`) выводится из авторского диалекта и
  расширения файла. Он MUST NOT указываться автором.
- **`depends`** выводится из SQL AST (`dialect.table_refs()`). Если он написан, компилятор
  MUST завершаться ошибкой при расхождении объявления с AST. `depends`, лишь повторяющий AST,
  SHOULD опускаться.

## 5. Колонки

Компактный табличный синтаксис, одна колонка на строку: `name  type  attribute*`. Простые
атрибуты остаются в строке; длинные метаданные разворачиваются ниже как строки
`namespace.key value` с отступом.

```
columns:
  game_sk      varchar   pk !null unique
  country_id   bigint    fk(core.country.id)
    fk.relationship   many-to-one
    fk.validation     warn
```

Базовый словарь атрибутов: `pk` · `bk` · `fk(<model>.<column>)` · `!null` · `unique` ·
`generated` · `deprecated` · `pii`.

Инлайн-атрибуты ограничений — это именованные вендор-нейтральные проверки с необязательными
аргументами — `non_negative`, `between(0,5)` — из переносимого словаря проверок реализации
(имена, которые умеют отрисовать все её адаптеры; для OGIP сегодня: `not_null` через `!null`,
`unique`, `non_negative`, `between`). Атрибут вне базового словаря, зарезервированных
пространств имён и словаря проверок MUST приводить к ошибке компиляции.

Зарезервированные для роста пространства имён: `scd2.*` · `dv2.*` · `cdc.*` · `dq.*` ·
`metric.*` · `semantic.*` · `partition.*` · `cluster.*`. Пространство имён MUST NOT
заполняться раньше, чем оно понадобится модели.

## 6. Проверки

Простые ограничения остаются в строке колонки (§5). Всё, что имеет имя или межмодельную
ссылку, идёт в `checks:` — одна проверка на запись: имя и вендор-нейтральное выражение или
вызов функции-проверки.

```
checks:
  title_not_blank   expression(trim(title) <> '')
  valid_fk          relationship(game_id -> core.game.game_id)
```

Проверки — утверждения о корректности; адаптеры отрисовывают их нативно (тесты dbt, проверки
Bruin, аудиты SQLMesh). Мониторы — не проверки и MUST NOT появляться здесь (§1).

## 7. Импорты и макросы

Макросы — семантические операции, записываемые как `@ns.name(args)`. Пространства имён
импортируются и никогда не глобальны:

```
imports:
  odts.keys    as keys
  odts.dates   as dates
```

- Jinja MUST NOT появляться в ODTS-документе; она MAY существовать только в сгенерированных
  проектах.
- Макрос определяется один раз в реестре и компилируется нативно для каждого движка (SQLMesh
  `@DEF`, Jinja для dbt/Bruin, разворачивание в plain SQL).
- Каждый макрос MUST нести конформанс-тест: одна фикстура, прогнанная через каждый адаптер на
  авторском движке, с утверждением побайтово идентичного вывода. Ни один макрос не
  приземляется без него.
- Имя макроса, не разрешающееся в реестре, MUST приводить к ошибке компиляции.

## 8. Тело SQL

- Переносимый SQL на авторском диалекте; всё, что должно понимать SQL, парсит его (sqlglot) —
  сопоставление строк MUST NOT использоваться для переписывания ссылок или lineage.
- LValue-проекции используют только `:=` (`sk := md5(id)`); фронтенд десахаризует их, когда
  узел `PropertyEQ` — **непосредственный потомок списка проекций**; вложенный `:=` остаётся
  именованным аргументом движка. `=` как алиас проекции MUST отклоняться с ошибкой,
  указывающей на `:=` — он парсится как предикат равенства и даёт молча неверную булеву
  колонку.
- Pipe-синтаксис (`|>`) MUST NOT появляться в документах 0.1 (отложен, §10).
- Ссылки на другие модели используют точечное имя модели (`staging.stg_games`) как обычную
  табличную ссылку; адаптеры переписывают их нативно (`{{ ref(...) }}`, модельные ссылки
  SQLMesh) в границах AST, никогда не текстово.

## 9. Компиляция, IR и соответствие

Каноническая модель — типизированный IR, никогда не текст заголовка:

```
spec/sql/**/*.sql (@odts) ──▶ frontend ──▶ rendered legacy YAML header ──▶ parse_asset() ──▶ Asset IR ──▶ adapters
```

Для OGIP фронтенд рендерит `@odts` в легаси-текст YAML-заголовка `@bruin` (требуемый дословно
одной из целей), который питает неизменённый конвейер `parse_asset()` и шесть адаптеров.
Отрендеренный YAML MUST NOT коммититься. Оба маркера остаются валидными во время миграции;
фронтенд диспетчеризуется по `/* @odts` против `/* @bruin`.

Соответствующая реализация MUST тестировать:

- **round-trip** — для каждой мигрированной модели отрендеренный легаси-заголовок эквивалентен
  прежнему, написанному вручную;
- **утверждение `depends`** — написанный автором `depends`, противоречащий AST, падает;
- **LValue** — `x = y` в проекции отклоняется; `x := y` десахаризуется, вложенный `:=`
  сохраняется;
- **соответствие макросов** — побайтово идентичный вывод для каждого адаптера (§7);
- **перегенерация целей** — все объявленные цели компилируются, и закоммиченный
  сгенерированный вывод совпадает со свежей компиляцией (`spec-compile` / `spec-verify`).

Канонический форматтер один (sqlfluff для OGIP); второй форматтер MUST NOT вводиться.
Форматирование никогда не меняет семантику.

## 10. Отложено из 0.1

Отложено — с брифом как проектным авторитетом; не принято как синтаксис расширений, пока их не
определит какая-либо версия: pipe-синтаксис (`|>`, десахаризуемый фронтендом) · директива
диалекта/возможностей `sql` · семантическая директива `type` · стратегии `materialize` за
пределами `table`/`view` (словарь OTS: `incremental` с `delete_insert`/`append`/`merge`,
`scd2`) · директивы `grain` / `key` · директива `doc`/`description` · блоки `monitors:` и
`metrics:` · `include`. Версии грамматики на уровне блоков **отклонены** ADR-0016, а не
отложены.
