# Proposal — compact projection, shared header fragment, macro files (`0.2.man` sketch)

**Status:** design input · not accepted · not normative
**Against:** [ODTS 0.1](../SPEC.md) · design authority [GOVERNING-BRIEF.md](../GOVERNING-BRIEF.md)
**Origin:** hand-authored sketch by the standard owner, recorded verbatim below.

This is a syntax proposal, evaluated in the form the brief mandates
(motivation · grammar · examples · IR mapping · compiler implications · backward compatibility ·
tradeoffs). Parts of it are recommended for a future version; parts are rejected outright, with
the reason recorded so they are not re-proposed. Nothing here changes [SPEC.md](../SPEC.md).

## Source — recorded verbatim

Three documents concatenated in one scratch file: a macro file, a shared header fragment, and
the model.

```
# stg/stg.mac
meta_cols():
   ingested_at    := _ingested_at::timestamp
 , etl_batch_id


# stg/_common.odts
owner     data-eng@ogip
#staging

select
    {{ result_cols }}
    , @stg.meta_cols

# stg/stg_metacritic_games.sql
/* @odts 0.2.man
table
#metacritic #daily
*/
from raw.metacritic__game
select
       slug           str                   uniq
     , name           str
     , released_date  := released::date?
     , genre
     , publisher
     , metascore      := metascore::int     | >0
     , review_count   := review_count::int
     , content_hash
     , source_url
```

Compare with the accepted 0.1 authoring of the same model:
[`examples/staging/stg_metacritic_games.sql`](../examples/staging/stg_metacritic_games.sql).

## 1. Motivation

The 0.1 header states every column twice — once in `columns:` for metadata, once in the
`select` for computation — and repeats `owner` and the layer tag in all 16 live `spec/sql`
models. The sketch attacks both: metadata rides on the projection line, and everything constant
across a layer moves into one shared fragment. On this model it is 24 lines against 31, and the
two column lists can no longer disagree with each other because there is only one.

That is a real problem correctly identified. The disagreement it prevents is not hypothetical:
the 0.1 fixture for this very model shipped `metascore non_negative` while the live model
declared `between(0, 100)`, and no gate caught it (now guarded by
`test_odts_fixture_checks_match_spec_sql`).

## 2. Verdict per element

| Element | Verdict | Reason |
|---|---|---|
| Shared header fragment (`_common.odts`) | **carry forward** | Removes per-model `owner`/layer-tag repetition; maps to the brief's `include`, deferred in [SPEC.md §10](../SPEC.md) |
| `model` inferred from path | **carry forward** | §2 already says the name SHOULD equal `<parent-dir>.<file-stem>`; §4 says a derivable directive MUST NOT be required |
| `::` cast + `?` try-cast marker | **carry forward, needs grammar** | `released::date?` against `try_cast(released as date) as released_date` is a real saving; `?` is new and undefined |
| Macro files (`.mac`) | **carry forward, narrowed** | Registry is already planned ([#36](https://github.com/dataengy/ogip/issues/36)); see §5 for why projection-fragment macros are the hard case |
| Metadata on the projection line | **goal yes, encoding no** | See below — breaks the SQL body |
| `{{ result_cols }}` | **reject** | Jinja |
| `0.2.man` version | **reject** | Not a grammar version |
| `#tag` shorthand · `str`/`int` aliases · `\| >0` checks · bare `table` for `kind` | **reject as written** | New closed-vocabulary entries, no grammar or IR mapping given |

### Why the projection encoding is rejected

`slug str uniq` is not SQL. [SPEC.md §8](../SPEC.md) requires the body be parsed —
"everything that must understand the SQL parses it (sqlglot); string matching MUST NOT be used
for reference rewriting or lineage" — and the brief's own proposal checklist asks, question 7,
*"Would SQLGlot AST still represent the SQL?"*. Here it would not: the frontend would have to
strip metadata textually before sqlglot ever saw the body, which is exactly the string-matching
step both documents forbid, and it would do so on the one construct where getting it wrong
silently mis-parses the model.

`{{ result_cols }}` is a harder no: the brief says *"Never use Jinja inside ODTS"* and §7 says
*"Jinja MUST NOT appear in an ODTS document; it MAY exist only in generated projects."* The
sketch uses it for template inheritance — the fragment owns the `select` skeleton, the model
fills the hole. That mechanism needs a native form (§5), not a templating engine.

**The salvageable variant:** attach metadata only to `:=` projections, which are already
normative and already desugared by the frontend (§8), and let the compiler lift the attributes
into the IR's column table:

```
select
      slug          := slug                  uniq !null
    , metascore     := metascore::int        between(0,100)
```

Every line stays a `PropertyEQ` node sqlglot can represent, and the metadata is a trailing
attribute list on a node the frontend already rewrites. Columns needing metadata pay one `:=`;
columns needing none stay bare. This preserves the motivation without the unparseable body.

## 3. Grammar (for the carried-forward parts only)

```
document      := fragment-ref? header body
header        := "/* @odts" version NEWLINE directive* "*/"
fragment-ref  := "include" ws path            # resolves before directive parsing
projection    := name ":=" expression attribute*
cast-expr     := expression "::" type "?"?    # "?" = try-cast, NULL on failure
attribute     := core-attr | check-call       # unchanged from §5
```

`include` resolves at parse time into the including document's directive stream; a directive in
the including document overrides the fragment. Fragments carry directives only — never SQL,
which is what forces the Jinja in the sketch and is the point of rejecting it. One level, no
transitive includes: a fragment that includes a fragment is a build system, and the brief asks
whether a recursive descent parser stays simple (question 6).

## 4. IR mapping

Nothing here reaches the adapters as new IR. All of it collapses in the frontend:

- `include` → directives merged into the same `Asset` fields the 0.1 header populates; the IR
  cannot tell an inherited `owner` from an authored one.
- inferred `model` → the existing `name` field, filled from the path rather than the header.
- `x := expr::type?` → `Alias(this=TryCast(...), alias=x)`, the same node
  `try_cast(expr as type) as x` already produces. Identical IR, identical adapter output.
- projection-carried attributes → lifted out of the projection into the IR's existing column
  table before adapters run. Adapters see today's structure.

This is the test of the whole proposal: **the IR must not change.** Every rejected element
above is rejected partly because it *would* change it.

## 5. Compiler implications

- **`include` needs a cycle check and a deterministic merge order**, or two models with the
  same header text compile differently depending on resolution order.
- **Fragments break single-file readability.** A model's real `owner` is no longer visible in
  the model. Mitigation: the canonical formatter (§9) can render the resolved header on
  request; the compile error must name the fragment, not the model, when a fragment is wrong.
- **`?` must map to each target's try-cast**, and targets disagree on failure semantics
  (silent NULL vs error). It needs the same conformance test the macro registry needs
  ([#36](https://github.com/dataengy/ogip/issues/36)): one fixture, every adapter, byte-identical
  output. A cast that silently NULLs on one engine and raises on another is the
  `dbt_utils.generate_surrogate_key` failure mode again — wrong data, discovered far downstream.
- **Projection-fragment macros (`@stg.meta_cols` expanding to several columns) are a different
  species** from the scalar `@keys.hash(x)` the registry is scoped to. A macro that emits *n*
  columns changes the model's schema, so column metadata and the macro's output must be
  validated together. Land scalar macros first; this is a separate proposal.

## 6. Backward compatibility

Additive and safe, if versioned properly. A 0.1 document remains valid: it has no `include`, no
`::`, and its `columns:` block keeps working. A 0.2 document using these features does not parse
as 0.1 — correct, and why the version line matters.

`0.2.man` is rejected precisely here. [SPEC.md §2](../SPEC.md) requires the first line be
`@odts <version>` and states that per-block grammar versions were **rejected** by
[ADR-0016](../../../docs/adr/ADR-0016-odts-authoring-format-spec-sql.md), not deferred. A `.man`
suffix reintroduces that by another route: a private dialect no compiler can be written against
and no "backward compatible" claim can be checked against. Grammar versions are `0.1`, `0.2`.

## 7. Tradeoffs

**In favour:** fewer lines; the duplicate column list disappears, and with it a real class of
silent drift; less repetition across 16 models; every carried-forward element is frontend-only.

**Against:** a model stops being readable in one file; `?` adds a second cast spelling
(`try_cast` still parses) — the brief prefers less syntax, and two ways to try-cast is more;
`include` is the first ODTS feature where compile output depends on a second file, so error
messages and formatter behaviour both get harder; and the compaction that motivates the whole
sketch is largely delivered by `include` alone, without touching the projection at all.

**Recommended sequence:** `include` first — most of the saving, least of the risk, and no
change to the SQL body. Then `::`/`?` with a cast-conformance test. Projection-carried metadata
last if at all, in the `:=`-only form of §2, and only once the macro registry has shown that a
frontend rewrite of the projection list is safe in practice.

## Not carried forward, for the record

`#tag` shorthand, `str`/`int` type aliases, `| <op>` check shorthand, and bare `table` for
`kind` are each a new entry in a closed vocabulary ([SPEC.md §3](../SPEC.md) directives,
[§5](../SPEC.md) attributes and types). None is unreasonable; none was proposed with a grammar,
an IR mapping, or a migration for existing documents, and the brief is explicit that syntax
does not enter without justification.

`| >0` also loses information the current vocabulary carries: the live model constrains
`metascore` to `between(0, 100)`, and `>0` admits `150` while rejecting a legitimate `0`. A
shorthand that cannot express what the long form already expresses is not a shorthand.
