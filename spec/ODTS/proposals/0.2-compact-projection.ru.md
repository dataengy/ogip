# Предложение — компактная проекция (compact projection), общий фрагмент заголовка, файлы макросов (набросок `0.2.man`)

**Статус:** входной материал дизайна · не принято · не нормативно
**Оценивается против:** [ODTS 0.1](../SPEC.md) · авторитет дизайна — [GOVERNING-BRIEF.md](../GOVERNING-BRIEF.md)
**Происхождение:** написанный вручную набросок владельца стандарта, записан дословно ниже.

Это синтаксическое предложение (proposal), оценённое в форме, которую предписывает бриф
(мотивация · грамматика · примеры · отображение в IR · последствия для компилятора ·
обратная совместимость · компромиссы). Часть его рекомендована для будущей версии; часть
отклонена сразу — с записанной причиной, чтобы её не предлагали заново. Ничто здесь не
меняет [SPEC.md](../SPEC.md).

## Источник — записан дословно

Три документа, склеенные в одном черновом файле: файл макросов, общий фрагмент заголовка и
сама модель.

```
# stg/stg.mac
meta_cols():
   ingested_at    := _ingested_at::timestamp
 , etl_batch_id


# stg/_common.odts
owner     data-eng@ogip
#staging

select
    {{ result_cols }}
    , @stg.meta_cols

# stg/stg_metacritic_games.sql
/* @odts 0.2.man
table
#metacritic #daily
*/
from raw.metacritic__game
select
       slug           str                   uniq
     , name           str
     , released_date  := released::date?
     , genre
     , publisher
     , metascore      := metascore::int     | >0
     , review_count   := review_count::int
     , content_hash
     , source_url
```

Сравните с принятым авторингом 0.1 той же модели:
[`examples/staging/stg_metacritic_games.sql`](../examples/staging/stg_metacritic_games.sql).

## 1. Мотивация

Заголовок 0.1 указывает каждую колонку дважды — один раз в `columns:` для метаданных, один
раз в `select` для вычисления — и повторяет `owner` и тег слоя во всех 16 живых моделях
`spec/sql`. Набросок атакует обе проблемы: метаданные едут на строке проекции, а всё
постоянное в пределах слоя переезжает в один общий фрагмент. На этой модели это 24 строки
против 31, и два списка колонок больше не могут разойтись между собой, потому что список
только один.

Это реальная, верно определённая проблема. Расхождение, которое он предотвращает, не
гипотетично: фикстура 0.1 для этой самой модели ушла с `metascore non_negative`, тогда как
живая модель объявляла `between(0, 100)`, и ни один гейт этого не поймал (теперь охраняется
`test_odts_fixture_checks_match_spec_sql`).

## 2. Вердикт по элементам

| Элемент | Вердикт | Причина |
|---|---|---|
| Общий фрагмент заголовка (`_common.odts`) | **перенести дальше** | Убирает повторение `owner`/тега слоя в каждой модели; отображается на `include` из брифа, отложенный в [SPEC.md §10](../SPEC.md) |
| Вывод `model` из пути | **перенести дальше** | §2 уже говорит, что имя SHOULD совпадать с `<parent-dir>.<file-stem>`; §4 говорит, что выводимая директива MUST NOT быть обязательной |
| Каст `::` + маркер try-cast `?` | **перенести дальше, нужна грамматика** | `released::date?` против `try_cast(released as date) as released_date` — реальная экономия; `?` — новый и неопределённый |
| Файлы макросов (`.mac`) | **перенести дальше, с сужением** | Реестр уже запланирован ([#36](https://github.com/dataengy/ogip/issues/36)); см. §5 о том, почему макросы-фрагменты проекции — трудный случай |
| Метаданные на строке проекции | **цель — да, кодирование — нет** | См. ниже — ломает тело SQL |
| `{{ result_cols }}` | **отклонить** | Jinja |
| Версия `0.2.man` | **отклонить** | Не версия грамматики |
| Сокращение `#tag` · алиасы `str`/`int` · проверки `\| >0` · голое `table` вместо `kind` | **отклонить в предложенном виде** | Новые записи закрытого словаря; ни грамматики, ни отображения в IR не дано |

### Почему кодирование на проекции отклонено

`slug str uniq` — это не SQL. [SPEC.md §8](../SPEC.md) требует, чтобы тело парсилось —
«всё, что должно понимать SQL, парсит его (sqlglot); сопоставление строк MUST NOT
использоваться для переписывания ссылок или lineage», — а собственный чек-лист предложений
в брифе задаёт вопрос 7: *«Будет ли AST SQLGlot по-прежнему представлять этот SQL?»*.
Здесь — не будет: фронтенду пришлось бы текстуально срезать метаданные до того, как sqlglot
вообще увидит тело, а это ровно тот шаг сопоставления строк, который запрещают оба
документа, — причём на той самой конструкции, где ошибка молча ведёт к неверному разбору
модели.

`{{ result_cols }}` — ещё более жёсткое «нет»: бриф говорит *«Никогда не используйте Jinja
внутри ODTS»*, а §7 говорит *«Jinja MUST NOT появляться в документе ODTS; она MAY
существовать только в сгенерированных проектах»*. Набросок использует её для наследования
шаблонов — фрагмент владеет каркасом `select`, модель заполняет дыру. Этому механизму нужна
нативная форма (§5), а не шаблонизатор.

**Спасаемый вариант:** прикреплять метаданные только к проекциям с `:=`, которые уже
нормативны и уже десугарятся фронтендом (§8), и позволить компилятору поднимать атрибуты в
таблицу колонок IR:

```
select
      slug          := slug                  uniq !null
    , metascore     := metascore::int        between(0,100)
```

Каждая строка остаётся узлом `PropertyEQ`, который sqlglot умеет представлять, а метаданные
— хвостовой список атрибутов на узле, который фронтенд и так переписывает. Колонки, которым
нужны метаданные, платят одним `:=`; колонки без метаданных остаются голыми. Это сохраняет
мотивацию без непарсимого тела.

## 3. Грамматика (только для переносимых частей)

```
document      := fragment-ref? header body
header        := "/* @odts" version NEWLINE directive* "*/"
fragment-ref  := "include" ws path            # resolves before directive parsing
projection    := name ":=" expression attribute*
cast-expr     := expression "::" type "?"?    # "?" = try-cast, NULL on failure
attribute     := core-attr | check-call       # unchanged from §5
```

`include` разрешается во время парсинга в поток директив включающего документа; директива
во включающем документе переопределяет фрагмент. Фрагменты несут только директивы — никогда
SQL: именно SQL вынуждает Jinja в наброске, и в этом суть его отклонения. Один уровень, без
транзитивных include: фрагмент, включающий фрагмент, — это уже система сборки, а бриф
спрашивает, останется ли парсер рекурсивного спуска простым (вопрос 6).

## 4. Отображение в IR

Ничто отсюда не доходит до адаптеров как новый IR. Всё схлопывается во фронтенде:

- `include` → директивы сливаются в те же поля `Asset`, которые заполняет заголовок 0.1; IR
  не может отличить унаследованный `owner` от авторского.
- выведенный `model` → существующее поле `name`, заполняемое из пути, а не из заголовка.
- `x := expr::type?` → `Alias(this=TryCast(...), alias=x)` — тот же узел, который уже
  порождает `try_cast(expr as type) as x`. Идентичный IR, идентичный вывод адаптеров.
- атрибуты на проекции → поднимаются из проекции в существующую таблицу колонок IR до
  запуска адаптеров. Адаптеры видят сегодняшнюю структуру.

Это тест всего предложения: **IR не должен меняться.** Каждый отклонённый выше элемент
отклонён отчасти потому, что он *менял бы* IR.

## 5. Последствия для компилятора

- **`include` нужны проверка циклов и детерминированный порядок слияния**, иначе две модели
  с одинаковым текстом заголовка компилируются по-разному в зависимости от порядка
  разрешения.
- **Фрагменты ломают читаемость в одном файле.** Реальный `owner` модели больше не виден в
  самой модели. Смягчение: канонический форматтер (§9) может по запросу отрисовать
  разрешённый заголовок; ошибка компиляции должна называть фрагмент, а не модель, когда
  неверен фрагмент.
- **`?` должен отображаться в try-cast каждой цели**, а цели расходятся в семантике отказа
  (тихий NULL против ошибки). Ему нужен тот же тест соответствия, что и реестру макросов
  ([#36](https://github.com/dataengy/ogip/issues/36)): одна фикстура, каждый адаптер,
  побайтово идентичный вывод. Каст, который на одном движке тихо даёт NULL, а на другом
  бросает ошибку, — это снова режим отказа `dbt_utils.generate_surrogate_key`: неверные
  данные, обнаруженные далеко ниже по потоку.
- **Макросы-фрагменты проекции (`@stg.meta_cols`, разворачивающийся в несколько колонок) —
  другой вид**, нежели скалярный `@keys.hash(x)`, которым ограничен реестр. Макрос,
  порождающий *n* колонок, меняет схему модели, поэтому метаданные колонок и вывод макроса
  должны валидироваться вместе. Сначала приземлите скалярные макросы; это отдельное
  предложение.

## 6. Обратная совместимость

Аддитивно и безопасно — при правильном версионировании. Документ 0.1 остаётся валидным: в
нём нет `include`, нет `::`, и его блок `columns:` продолжает работать. Документ 0.2,
использующий эти фичи, не парсится как 0.1 — это корректно, и именно поэтому важна строка
версии.

`0.2.man` отклоняется именно здесь. [SPEC.md §2](../SPEC.md) требует, чтобы первая строка
была `@odts <version>`, и констатирует, что поблочные версии грамматики были **отклонены**
[ADR-0016](../../../docs/adr/ADR-0016-odts-authoring-format-spec-sql.md), а не отложены.
Суффикс `.man` возвращает то же самое другим путём: приватный диалект, под который нельзя
написать компилятор и относительно которого нельзя проверить заявление об «обратной
совместимости». Версии грамматики — `0.1`, `0.2`.

## 7. Компромиссы

**За:** меньше строк; исчезает дублирующий список колонок, а с ним — реальный класс тихого
дрейфа; меньше повторов в 16 моделях; каждый переносимый дальше элемент затрагивает только
фронтенд.

**Против:** модель перестаёт читаться в одном файле; `?` добавляет второе написание каста
(`try_cast` по-прежнему парсится) — бриф предпочитает меньше синтаксиса, а два способа
try-cast — это больше; `include` — первая фича ODTS, где вывод компиляции зависит от
второго файла, так что и сообщения об ошибках, и поведение форматтера усложняются; и
компактификация, мотивирующая весь набросок, по большей части достигается одним `include`,
вообще без прикосновения к проекции.

**Рекомендуемая последовательность:** сначала `include` — большая часть экономии,
наименьший риск и никаких изменений тела SQL. Затем `::`/`?` с тестом соответствия кастов.
Метаданные на проекции — последними, если вообще, в форме «только `:=`» из §2, и лишь после
того, как реестр макросов покажет, что фронтендное переписывание списка проекций безопасно
на практике.

## Не перенесено дальше — для протокола

Сокращение `#tag`, алиасы типов `str`/`int`, сокращение проверок `| <op>` и голое `table`
вместо `kind` — каждое из них новая запись в закрытом словаре (директивы
[SPEC.md §3](../SPEC.md), атрибуты и типы [§5](../SPEC.md)). Ни одно не является
неразумным; ни одно не было предложено с грамматикой, отображением в IR или миграцией
существующих документов, а бриф прямо говорит, что синтаксис не входит без обоснования.

`| >0` к тому же теряет информацию, которую несёт текущий словарь: живая модель
ограничивает `metascore` через `between(0, 100)`, а `>0` пропускает `150`, отвергая при
этом легитимный `0`. Сокращение, которое не может выразить то, что уже выражает длинная
форма, — не сокращение.
