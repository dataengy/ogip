# Нормативный профиль ODOS 0.1

**Статус:** утверждённый профиль OGIP  
**Версия:** 0.1  
**Область применения:** Dagster 1.13 и Prefect 3.4 или новее

Ключевые слова **MUST**, **MUST NOT**, **SHOULD** и **MAY** являются нормативными.

## 1. Граница

ODOS описывает оркестрацию: джобы, нативные для оркестрации активы, автоматизации, проверки,
хуки, партиции, повторы, конкурентность и реакции на сбои. Трансформации принадлежат ODTS и
MUST NOT встраиваться в ODOS. Конфигурация инстанса/развёртывания и оркестраторные Components
MUST оставаться вне портируемых документов ODOS.

Реализация MUST поддерживать ровно те цели, которые она объявляет. Профиль OGIP 0.1 объявляет
`dagster` и `prefect`. Конструкция, которую невозможно спроецировать на запрошенную цель, MUST
приводить к ошибке компиляции, если только её объект не несёт явного ограничения `targets`.
Молчаливое опускание запрещено.

## 2. Документы и версионирование

Групповой документ ODOS — это YAML со следующими обязательными ключами верхнего уровня:

```yaml
odos: 0.1
group: warehouse
```

Он MAY содержать `doc`, `assets`, `jobs`, `automations`, `checks` и `hooks`. Один файл
представляет одну группу. Каждый объект в этих секциях MAY содержать `doc`, `tags` и `targets`.
Неизвестные ключи MUST отклоняться.

Версия относится ко всему файлу. Блоки MUST NOT нести независимые версии.

Документы используют семантику YAML 1.2. Авторам SHOULD брать ключ `"on"` в кавычки, чтобы
загрузчики, совместимые с YAML 1.1, не приводили его к булеву ключу `true`.

`_defaults.yml` — отдельная форма документа. Она требует `odos`, `owner` и `registry` и MAY
определять именованные `partitions` и джобовые `defaults`. Значения по умолчанию сливаются в
каждый джоб; явное значение джоба имеет приоритет.

## 3. Имена и реестр задач

Ключи активов и имена задач — точечные идентификаторы, такие как `core.game` и `dbt.build`.
Нативные для оркестратора кортежи ключей и пути импорта MUST NOT появляться в портируемой форме.

Каждый `task` и каждый вызываемый объект, именуемый в `poll(...)`, MUST разрешаться в
настроенном закрытом реестре задач. Функции реестра MUST быть обычными типизированными
функциями, адресуемыми по имени. Неизвестное имя MUST приводить к ошибке компиляции. Лазейка
запуска через шелл не входит в ODOS 0.1.

## 4. Джобы

Джоб имеет ровно одну из двух форм:

- ассет-джоб: `select`;
- задачный джоб: `task`, опционально с именованными `args`.

Грамматика выборки намеренно закрыта:

```text
name | name+ | +name | tag:name
```

Выборка MAY быть одним выражением или непустым списком. `name+` — замыкание вниз по потоку,
а `+name` — замыкание вверх по потоку. Компилятор MUST разворачивать выборки по графу линеажа
ODTS плюс нативным для ODOS активам.

`partitioned: true` валидно только тогда, когда каждый выбранный актив разделяет одно
именованное определение партиций. Компилятор MUST отклонять смешанное или отсутствующее
определение партиций.

Джобы MAY определять:

```yaml
retry: { max_attempts: 3, type: exponential, interval: PT1M }
concurrency: { limit: 1, behavior: cancel }
on_failure: alerting.notify_run_failure
```

Интервалы повторов MUST использовать длительности ISO-8601. Тип повтора — `constant` или
`exponential`. Поведение конкурентности — `queue`, `cancel` или `fail`.

## 5. Активы

`assets` объявляет только активы, которых нет ни в ODTS, ни во внешнем компоненте. Актив
требует реестровый `task` и MAY определять именованные `partitions`, `kinds` и `group_name`.
Портируемые ключи активов остаются точечными именами; за их конкретное отображение отвечают
целевые адаптеры.

## 6. Автоматизации

Автоматизация имеет одно выражение `on` из этого закрытого набора:

```text
cron("<cron>")
asset_materialized(<asset>)
poll(<registry-name>, every=<duration>)
partition_ready(<job>)
```

Первые три формы требуют `run`, именующего джоб в той же скомпилированной модели.
`partition_ready(...)` именует свой джоб в самом выражении и MUST NOT дополнительно объявлять
`run`.

Вызываемые объекты `poll` возвращают токен курсора или `None`. Dagster может владеть курсором
нативно; проекция Prefect требует внешнего хранилища курсоров. Выбор этого хранилища —
решение реализации, но обе проекции MUST сохранять идентичную семантику сравнения.

`asset_materialized` проецируется на нативные события активов в обеих целях. Реализации MUST
документировать, что кэшированные задачи Prefect не эмитят событие материализации.

## 7. Проверки и хуки

Проверка требует `asset` и реестровый `task` и MAY задавать `blocking`. Проверки — это шлюзы
корректности. Свежесть, аномалии объёма и дрейф схемы — вопросы наблюдаемости и находятся вне
этой секции.

Хук требует `on`, `task` и явного ограничения `targets`. ODOS 0.1 определяет выражение с
областью действия location — `run_failed(scope=location)`. Портируемая обработка сбоев SHOULD
использовать `on_failure` уровня джоба; хуки — для действительно специфичной для цели области
действия.

## 8. Требования к возможностям

| Конструкция | Dagster | Prefect | Требуемая проекция |
|---|---|---|---|
| джоб `select` | ассет-джоб | упорядоченный поток | выводится из графа ODTS |
| джоб `task` | job/op | flow/task | прямая |
| актив | asset | materialize | прямая |
| `cron` | schedule | расписание деплоймента | прямая |
| `asset_materialized` | asset sensor | реактивная событийная автоматизация | прямая |
| `poll` | сенсор с курсором | опрос по расписанию + внешний курсор | эквивалентная семантика |
| `partition_ready` | партиционное расписание | cron + аргумент партиции | эквивалентная семантика |
| проверка | asset check | валидационная задача после актива | эквивалентный результат |
| location-хук | run-failure sensor | недоступно | ограничено целью |
| устойчивость | нативно | нативно | прямая |

## 9. Компиляция и соответствие

Фронтенд MUST:

1. валидировать закрытый словарь YAML;
2. сливать значения по умолчанию;
3. разрешать имена задач и `poll` по реестру;
4. разрешать перекрёстные ссылки джобов, партиций, активов и автоматизаций;
5. разворачивать выборки по линеажу ODTS;
6. соблюдать политику возможностей/сбоев;
7. эмитить типизированное промежуточное представление до целевого рендеринга.

Для каждого джоба, спроецированного на обе цели, тесты соответствия MUST утверждать одну и ту
же упорядоченную последовательность задач реестра с идентичными именованными аргументами.
Соответствующая реализация MUST также тестировать:

- успешную компиляцию каждой группы для каждой запрошенной цели;
- успешную загрузку целевых определений;
- совпадение закоммиченного сгенерированного вывода со свежей компиляцией;
- падение на неизвестных ключах и именах задач;
- падение непроецируемых объектов без `targets`.

## 10. Отложено из 0.1

Графы уровня задач внутри джоба, параметризованные входы и объявления политики бэкфилла
отложены. Они не принимаются как ключи-расширения: правило закрытого словаря продолжает
действовать.
