# OGIP — Открытые вопросы по требованиям

Неизвестные в требованиях, которые формируют архитектурные выборы, но не могут быть решены
изнутри репозитория — им нужны числа или намерение от потребителей данных (команда DS/ML) или
владельца данных. Каждая запись фиксирует, что мы знаем, что открыто, **текущее умолчание**
(мы строим это, пока не сказано иное) и **триггер решения**, который переоткрывает вопрос.
Решённая запись переходит в [ADR](adr/) и здесь зачёркивается.

_Добавлено 2026-07-17, вместе с переприоритизацией скрейпинга/R2 ([ROADMAP](ROADMAP.md))._

## 1. Требования к скрейпингу — и покрывают ли их dlt/ingestr

**Known.** Примерно половина планируемых источников скрейпятся/парсятся, а не являются чистыми
API (HLTB, Metacritic; региональные ценовые обходы имеют форму API, но враждебны по объёму).
Паттерн приземления зафиксирован: скрейперы пишут в схему Postgres `landing`, dlt загружает
landing → raw Parquet ([ADR-0006](adr/ADR-0006-dlt-default-ingestion-postgres-landing.md) ·
[ADR-0014](adr/ADR-0014-resilient-scraping-concurrency.md)).

**Open.**

- Насколько враждебны реальные цели — страницы с JS-рендерингом? анти-бот (снятие отпечатков TLS,
  стены-испытания)? Где на лестнице эскалации (httpx → curl_cffi → Playwright) стоит каждый
  источник?
- Требуемая свежесть/периодичность на источник и объём страниц на обновление — это задаёт
  бюджет конкурентности и лимиты вежливости.
- Позиция по ToS/robots на источник: что вообще можно извлекать, хранить и переопубликовывать?
- Достаточно ли простого **dlt** на стороне *извлечения* (его REST-источник / хелпер scrapy),
  или тяжёлые источники оправдывают выделенный фреймворк? **ingestr — не скрейпер** — его роль
  остаётся загрузкой/CDC (landing → lake), согласно поэтапному `comparisons/dlt-vs-ingestr.md`
  _(Phase 9)_.

**Current default.** [ADR-0014](adr/ADR-0014-resilient-scraping-concurrency.md): асинхронный
httpx с ограниченной конкурентностью на домен внутри `ScraperSource`; извлечение at-least-once +
идемпотентный upsert в landing; без Scrapy, без браузерной автоматизации, пока конкретный
источник не потребует этого.

**Decision trigger.** Первый источник, который проваливает путь httpx (JS-стена / бот-стена) →
эскалация на источник: curl_cffi, затем Playwright. Более ~3 враждебных источников на лестнице →
пересмотреть Scrapy/управляемые альтернативы как решение по всему флоту.

## 2. Объём данных — сегодня и рост (Iceberg/DuckLake? Trino/Spark?)

**Known.** Сегодня lake — масштаба сэмпла: срез M0 гоняет одноузловой DuckDB над локальным
Parquet. Цель — масштаб каталога (~10⁵ игр) × временные ряды (отзывы, цены, число игроков),
что ещё долго умещается на одном мощном узле.

**Open.**

- Фактический объём сейчас (ГБ, число файлов, строки на источник) и рост по периодичности обновления.
- Бюджет пересборки: сколько может занимать полная пересборка, прежде чем инкремент станет обязательным?
- Конкурентность: сколько писателей (параллельные flow) и читателей (сессии DS) касаются lake
  одновременно?

**Current default.** Простой Parquet + DuckDB
([ADR-0002](adr/ADR-0002-duckdb-analytical-engine.md) ·
[ADR-0003](adr/ADR-0003-parquet-lake-defer-iceberg-ducklake.md)); один писатель на датасет;
R2 как облако записи истины.

**Decision trigger** (любое из):

- Горячий lake за пределами нескольких сотен ГБ, или полная пересборка, превышающая окно →
  **DuckLake или Iceberg** для снимков/уплотнения/ACID (ADR-0003 уже готовит это сравнение).
- Конкурентные писатели в одну таблицу, или DS требует машины времени → то же.
- Соединения, выходящие за один узел, или несколько движков, которым нужны те же таблицы
  одновременно → **Trino** (федеративный SQL над lake) раньше, чем **Spark** (только если тяжёлые
  Python/ML-трансформации должны выполняться *внутри* движка lake). И то, и другое — замена
  потребителя, а не переписывание lake — Parquet(/Iceberg) остаётся контрактом.

## 3. Формат хранения и инструменты управления данными — FS / семантика / быстрая отдача

**Known.** Продукт — **файлы** (ML-ready Parquet), не бэкенд приложения и не BI
([ADR-0009](adr/ADR-0009-ml-outputs-feature-store.md)). Feature store = SQL-как-FS
(`fs_*`); семантические определения — движко-независимые данные в `spec/`
([spec-semantic-layer](../.ai/tasks/spec-semantic-layer.md)); фреймворки живут только
в `experimental/`.

**Open.**

- Нужна ли какому-либо потребителю **отдача с низкой задержкой** (приложение, API, живые
  дашборды)? Файлы отвечают на пакетный DS; они не отвечают на 100-мс запросы. Если да →
  движок отдачи (**ClickHouse / StarRocks**), питаемый *из* витрин — никогда не заменяющий lake.
- Нужны ли какому-либо потребителю **онлайн-признаки** или более строгие point-in-time обучающие
  наборы, чем даёт SQL-как-FS? Если да → выделенный FS-инструмент (Feast/Featureform) — анализ
  внедрения запланирован как `comparisons/feature-store-tools.md` _(Phase 9)_.
- Появятся ли не-SQL потребители метрик (BI, self-serve)? Если да → семантический движок
  (**Cube / MetricFlow**), читающий семантические определения из `spec/`; до тех пор определения
  остаются данными, а движки — демонстрациями.
- Управление форматом таблиц (эволюция схемы, ретеншн, уплотнение): в какой момент ручная гигиена
  Parquet оправдывает DuckLake/Iceberg? (Связано с §2.)

**Current default.** Файлы + SQL-как-FS + семантика на уровне spec; без движка отдачи, без
FS-фреймворка, без семантического движка на продакшн-пути.

**Decision trigger.** *Именованный потребитель* с требованием по задержке / онлайну /
self-serve-метрикам — никогда не предпочтение инструмента само по себе.

## 4. Смешивание SQL и Python в трансформациях

**Known.** Слой трансформаций — SQL-first на DuckDB через SQLMesh
([ADR-0004](adr/ADR-0004-sqlmesh-default-transform-engine.md)). Но моделирование рынка —
кросс-источниковое разрешение сущностей, нечёткое сопоставление, инженерия признаков, всё
статистическое — со временем будет бороться с чистым SQL.

**Open.**

- Какая доля аналитического слоя нуждается в Python и где: парсинг до приземления (уже
  Python), очистка на staging или *внутри* моделируемого DAG?
- Если внутри DAG, поддержка движка становится решающей осью:
  - **SQLMesh** — Python-модели полноправны (тот же DAG, происхождение, аудиты) —
    текущее умолчание продолжает работать;
  - **dbt** — Python-модели фактически требуют рантайма хранилища
    (Snowflake/Databricks); тупик на DuckDB;
  - **OpenDBT** — латает ровно этот пробел dbt (локальные Python-модели); релевантен только
    если совместимость с dbt когда-либо станет требованием;
  - **Bruin** — гоняет Python-активы нативно рядом с SQL; усиливает существующую
    историю альтернативного профиля.
- Движок DataFrame для этих моделей: **Polars** (типизированный, ленивый, Arrow-нативный —
  кандидат по умолчанию) против Pandas (вездесущность, ноутбуки) против **PySpark** (только при
  кластерном масштабе — связано с §2).

**Current default.** SQL в SQLMesh. Трансформация, которая борется с SQL, становится **SQLMesh
Python-моделью** на Polars над Arrow; Pandas остаётся на уровне ноутбука/демо; без Spark.

**Decision trigger.** Первая продакшн-модель, чья SQL-версия нечитаема или медленнее, чем её
Python-эквивалент → реализовать как SQLMesh Python-модель и зафиксировать паттерн.
Если такие модели вырастут в большинство, пересмотреть выбор движка (Bruin/OpenDBT) в
сравнительных документах Phase-9.
