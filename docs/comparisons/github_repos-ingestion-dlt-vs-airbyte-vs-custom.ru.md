# Ингест `github_repos`: dlt против Airbyte против кастомного клиента

- **Дата:** 2026-07-23 · **Ссылки:** OGIP#18, OGIP#19
- **Источник:** `spec/sources/games/github_repos.yaml` (сертифицированное соответствие Airbyte, по итогам refit-аудита от 2026-07-20)
- **Сопутствующий документ:** `docs/superpowers/specs/2026-07-23-airbyte-terraform-lane-design.md`

## Почему «кастомный скрейпинг» для GitHub не рассматривается

GitHub предоставляет полные REST- и GraphQL-API, возвращающие те же данные в структурированном виде. HTML-скрейпинг
дал бы данные хуже и дороже, ломался бы при каждом редизайне и нарушал бы ToS. OGIP уже
разделяет `ApiSource` и `ScraperSource` (`ingestion/base/`); GitHub однозначно относится к первому.
Поэтому третий вариант ниже — это **кастомный клиент `ApiSource`**, а не буквальный скрейпинг, который проигрывает
по всем осям и исключается.

## Оговорка про dlt, проверенная

*Verified*-источник GitHub у dlt (`dlthub.com/docs/dlt-ecosystem/verified-sources/github`, проверено
2026-07-23) покрывает только `github_reactions` (GraphQL, полный рефреш) и `github_repo_events` (REST,
инкрементально по `created_at`). **Ни один** из шести стримов, нужных дескриптору — `repositories,
releases, stargazers, issues, commits, contributors` — не покрыт. Поэтому «dlt» здесь означает
`rest_api` + написанные вручную конфиги, а не готовый источник.

## Сравнение

| Ось | dlt (`rest_api`) | Airbyte (`source-github`) | Кастомный `ApiSource` |
|---|---|---|---|
| Готовое покрытие | verified-источник бесполезен → писать 6 конфигов стримов | 39 стримов, 26 инкрементальных, «из коробки» | писать всё |
| Сложность старта | средняя | **высокая** — abctl (k8s-in-docker) + Terraform + OAuth-приложение | средняя |
| Сложность на 6-м стриме | линейный рост | **~ноль** — стрим = строка конфига | линейный рост |
| GraphQL (`releases`) | вручную, вторая парадигма | внутри коннектора | вручную |
| Rate limits | наш код | ротация нескольких PAT + троттлинг, ожидания ≤240 мин | наш код |
| Инкрементальное состояние | dlt state, наша схема курсоров | по-репозиторно × по-стримно, внутренне | полностью наше |
| Кто чинит поломку API | мы | Airbyte (сертифицирован, GA) | мы |
| Мониторинг | Prefect-flow → **существующий obs-стек** | собственный k8s/UI/логи → **не в obs** | Prefect-flow → **существующий obs-стек** |
| Вес рантайма | процесс | кластер | процесс |
| Соответствие ADR-0006 | ✅ движок по умолчанию | ❌ только `experimental/` | ✅ |

## Оси, где различие неочевидно

**Возможности** — единственный крупный и честный плюс Airbyte: 39 стримов против 6, которые мы бы написали, REST+GraphQL
внутри. Будущая потребность в `workflow_runs`/`pull_request_stats` — это строка конфига для Airbyte и
спринт для двух других вариантов.

**Поддержка и эволюция** — Airbyte версионирует коннектор независимо; обновления приходят без нашего участия,
но так же приходят и поломки. dlt/кастом: мы владеем кодом — медленнее, но каждый сбой наш и
диагностируем. Заметьте: `source-github` — *единственный* коннектор из 591, который одновременно сертифицирован,
реальный код (Python CDK, а не только manifest) и читает публичные данные. Редкое исключение, а не норма.

**Стабильность и мониторинг — худшая ось Airbyte.** OGIP уже гоняет obs-стек
(VictoriaMetrics/Loki/Alloy/Grafana) + алертинг; dlt и кастом попадают в него автоматически, потому что
живут внутри Prefect-flow'ов. Airbyte — отдельный кластер со своим UI, логами и понятием
«sync failed»; чтобы направить его сбои в те же дашборды/алерты, нужна интеграция, которой
не существует. Для платформы, у которой наблюдаемость — заглавная фича, это не мелочь.

## SWOT

**dlt (`rest_api`)** — S: движок по умолчанию (ADR-0006), один рантайм, авто-наблюдаемость, декларативность для
REST. W: verified-источник не покрывает наши стримы; GraphQL `releases` ломает декларативную историю; rate
limits наши. O: стримы растут внутри существующего паттерна источника, переиспользуемого в остальных 17
источниках. T: «декларативность» тихо превращается в типизированный клиент, который мы сопровождаем — ровно та
стоимость, которую линия Airbyte обещала убрать.

**Airbyte (`source-github`)** — S: 39 стримов, REST+GraphQL, ротация токенов, троттлинг, внешнее
сопровождение, сертифицирован/GA. W: k8s-in-docker; вне obs; вне `make`-пути; целый слой Terraform;
OSS — только PAT. O: единственный источник, оправдывающий линию; даёт измеренный, а не
теоретический вердикт об инструменте. T: весь кейс держится на одном коннекторе; если он деградирует, линия теряет
своё обоснование. Прямой конфликт с брифом клиента: *«не подключать managed-коннекторы»*.

**Кастомный `ApiSource`** — S: полный контроль, точная типизация, в obs, ноль нового рантайма, соответствует тому,
что клиент называет реальной работой. W: мы пишем пагинацию, GraphQL, rate limits и state; дороже всего
на стрим. O: демонстрирует именно оплаченный навык («устойчивое извлечение»). T: переизобретает REST-половину dlt;
«контроль» рискует оказаться простым дублированием.

## Рекомендация

Разделить роли, а не короновать победителя:

- **Продуктовый путь → dlt.** Шесть стримов: пять чисто REST через `rest_api`, `releases` — отдельный GraphQL-
  ресурс. Соответствует ADR-0006, в obs, без кластера.
- **Airbyte → оставить экспериментом, каким он и является.** Его ценность не в лучшем ингесте; она в единственном
  честном измерении того, где сопровождаемый коннектор объективно выигрывает (39 стримов, две парадигмы,
  ротация токенов) и почему мы всё же держим его вне прода (наблюдаемость, вес рантайма, бриф
  клиента). Это тот самый «взгляд архитектора», которого требует контракт.
- **Кастомный `ApiSource` → не для GitHub.** Его место там, где API нет — «хвост» скрейпинга
  (SteamCharts, Metacritic, …).
