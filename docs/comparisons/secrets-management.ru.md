# Управление секретами — минимальный дефолт vs opt-in бэкенды

**Заданный вопрос:** как секреты путешествуют вместе с репозиторием — через CI, VPS и **новую
рабочую станцию** — никогда не попадая в git? **Вердикт: сохраняем минимальный дефолт
ADR-0011** (gitignored `.env` + секреты GitHub Actions); используем теперь реализованные
**opt-in бэкенды** (Bitwarden CLI, git-secret), когда второй машине нужны те же секреты
([ADR-0011](../adr/ADR-0011-minimal-secrets.md) ·
[#52](https://github.com/dataengy/ogip/issues/52)).

## Путь по умолчанию (без opt-in)

*Имена* слотов — это SSoT (`config/.env-render.py → SECRET_SLOTS`); `make render-env`
записывает их пустыми в gitignored корневой `.env`; вы заполняете их вручную. CI использует
шифрованные секреты GitHub Actions под теми же именами. Ноль зависимостей, нечего
синхронизировать — и нечему *синхронизироваться*: новая машина стартует с пустых слотов.

## Opt-in бэкенды (`config/.env-secrets-render.sh`)

Оба заполняют **только пустые** слоты (merge-safe — введённое вручную значение никогда не
перезаписывается) и никогда не печатают значения секретов. Бэкенд выбирается через
`config/config.yml → secrets.backend` или `--backend`; `just secrets-doctor` сообщает
готовность обоих, ничего не записывая.

| Измерение | **Bitwarden CLI** (`bw`) | **git-secret** (GPG) |
|---|---|---|
| Где живут секреты | ваш Bitwarden-vault (secure-note `OGIP .env.secrets`, скрытые поля по слотам) | в репозитории — закоммиченный шифрованный блоб `config/secrets/.env.secrets.secret` |
| Поток на новой машине | `bw login` → `export BW_SESSION="$(bw unlock --raw)"` → `just secrets-render` | импортируйте свой GPG-ключ → `just secrets-render` (бэкенд `git-secret`) |
| Поток на старой машине | `just secrets-push` (создаёт/обновляет элемент vault) | `just secrets-hide` → закоммитить `.secret`-блоб |
| Доп. аккаунт/ключ | аккаунт Bitwarden (здесь уже в ежедневном использовании) | GPG-ключевая пара, которую вы носите сами |
| Оффлайн clone-and-go | нет — vault должен быть доступен хотя бы раз | да — блоб уже в клоне |
| Мультипользовательский шаринг | vault sharing / коллекции организации | `git secret tell <email>` на каждый ключ получателя |
| История ротации | правка vault → `just secrets-render` везде | re-hide + commit; каждый клон подтягивает |
| Режим отказа, который надо знать | vault заблокирован ⇒ громкий стоп с командой разблокировки | нет GPG secret key ⇒ бэкенд неработоспособен (doctor так и говорит) |

## Рекомендация

- **Один человек, ≥2 машины, Bitwarden уже в ежедневном использовании (случай этого репо):**
  бэкенд Bitwarden — vault и есть подвижная часть, которой вы уже доверяете; ничего
  секретного никогда не лежит в репозитории.
- **Fork-and-run коллабораторы или air-gapped бутстрап:** git-secret — клон несёт блоб;
  цена — раздача ключей.
- **CI:** остаётся на секретах GitHub Actions независимо от локального opt-in.

Оба могут сосуществовать: блобы `git-secret` как внутрирепный эскроу, Bitwarden — как
повседневная синхронизация.

## Отклонено

- **Vault-демон / SOPS+KMS / облачные менеджеры секретов** — переусложнение для
  портфолио-платформы (та же логика, что сформировала
  [ADR-0011](../adr/ADR-0011-minimal-secrets.md)).
- **Коммит шифрованного полного `.env`** — производные несекретные значения теребили бы блоб
  на каждом изменении конфига; депонируются только слоты секретов.
