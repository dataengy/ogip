# ADR-0014 — Устойчивый скрапинг: async-first конкурентность, effectively-once landing

- **Status:** Proposed
- **Date:** 2026-07-17
- **Relates to:** PLAN A6 · D11 · [ADR-0006](ADR-0006-dlt-default-ingestion-postgres-landing.md) ·
  [OPEN-QUESTIONS §1](../OPEN-QUESTIONS.md)

## Context

Примерно половина планируемых источников OGIP собирается скрапингом или парсингом, а не забирается из чистых API (HLTB, Metacritic; региональные сборы цен по форме похожи на API, но враждебны по объёму). ADR-0006 фиксирует, *куда* попадают собранные данные (Postgres `landing` → dlt → raw Parquet), но не то, *как* ведёт себя сторона выборки. Сторона выборки нуждается в: устойчивом получении (повторы, изоляция сбоев, возобновляемость), вежливости к источнику (лимиты запросов, robots/ToS), landing без дубликатов при повторной доставке, полной наблюдаемости и модели конкурентности, которая масштабируется от одной страницы до сборов масштаба каталога без переписывания.

## Decision

`ScraperSource` реализует **один паттерн скрапинга**, переиспользуемый каждым скрапящим источником:

1. **Конкурентность — async-first.** Выборка ограничена вводом-выводом, поэтому `httpx.AsyncClient` + asyncio с **ограниченной конкурентностью**: глобальный лимит соединений и семафор на домен, оба читаются из config SSoT (`scraping.max_connections` · `scraping.per_domain`). Потоки для выборки не используются. **Процессы включаются опционально только для стадии парсинга** — `ProcessPoolExecutor` за `scraping.parse_workers` (по умолчанию `0` = inline), включается, когда профилирование показывает, что доминирует CPU-bound парсинг; функции парсинга остаются чистыми, поэтому пул подключается как drop-in.
2. **Вежливость.** Ограничение частоты по домену через token-bucket; экспоненциальный backoff с джиттером (tenacity) с учётом `Retry-After`; идентифицирующий User-Agent; разбор robots.txt/ToS, зафиксированный по источнику в его контракте; HTTP-кеширование (ETag / conditional GET) там, где источник это поддерживает.
3. **Устойчивость.** Таймауты на каждый вызов; бюджет повторов на URL; **circuit breaker** на домен (N последовательных сбоев → cooldown; запуск продолжается, домен помечается как degraded); неудачные выборки записываются в DLQ-таблицу — `landing.fetch_failures` (url, attempts, last error, fetched_at) — для последующего повтора. Частичный запуск — это нормальный запуск, а не падение.
4. **Effectively-once, а не «exactly-once».** Транспорт честно **at-least-once** (повторы могут перезапросить); upsert в landing **идемпотентен** (естественный ключ + хеш содержимого, `ON CONFLICT` update), поэтому нижестоящие потребители наблюдают ровно однократный *эффект*. Watermark-чекпоинты на пакет сущностей (`ingestion/common/watermark.py`) делают прерванные сборы возобновляемыми.
5. **Наблюдаемость.** Структурированные события loguru на каждую выборку (url, status, attempt, latency, bytes) в JSON-потоке логов пайплайна; счётчики по источникам (fetched · retried · failed · rate-limited · breaker-open), экспортируемые как метрики; алерты по свежести и частоте сбоев через `Notifier`.
6. **Лестница эскалации** для враждебных целей, решаемая для каждого источника и задокументированная в его контракте: чистый httpx (по умолчанию) → `curl_cffi` (соответствие TLS-fingerprint) → Playwright (рендеринг JS). Ничто выше httpx не попадает на прод-путь, пока это не потребуется конкретному источнику.

## Consequences

- Одна реализация устойчивости/вежливости обслуживает каждый скрапящий источник; код на источник сжимается до: обнаружения сущностей, конструирования URL, парсинга.
- API `ScraperSource` становится асинхронным (асинхронные генераторы); задача Prefect оборачивает его в `asyncio.run`, поэтому код flow остаётся синхронным.
- Ещё два landing-артефакта в сопровождении (DLQ-таблица, хранилище watermark) — цена возобновляемости и повтора.
- Заявления о гарантиях доставки проверяемы, а не преувеличены: выборка одной и той же страницы дважды должна давать одну строку в landing.
- Никакой сложности multiprocessing по умолчанию; пул парсинга существует только там, где это измерено.

## Alternatives considered

- **Scrapy** — зрелый, но приносит собственный event loop, стек middleware и раскладку проекта; дублирует то, чем уже владеют `BaseSource` + dlt (планирование, дедуп, экспорт). Отклонён для прод-пути; будет пересмотрен только если >3 тяжёлых источников создадут нагрузку на лестницу httpx ([OPEN-QUESTIONS §1](../OPEN-QUESTIONS.md)).
- **Выборка через пул потоков** — рабочий вариант, но хуже по backpressure и отмене, чем asyncio при высоком fan-out, без выигрыша от GIL для сетевых ожиданий. Отклонён как вариант по умолчанию.
- **Выборка multiprocessing-first** — память ×N и сложность IPC при нулевом выигрыше по вводу-выводу. Оставлено только как опциональный пул стадии парсинга.
- **Управляемые сервисы скрапинга (Zyte, Apify)** — хостируемая зависимость и стоимость за запрос; противоречит открытому, самохостируемому стеку. Исключено.
