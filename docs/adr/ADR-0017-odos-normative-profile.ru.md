# ADR-0017 — Нормативный профиль оркестрации ODOS 0.1

- **Статус:** Принято
- **Дата:** 2026-07-21
- **Связано с:** [ADR-0016](ADR-0016-odts-authoring-format-spec-sql.md) ·
  [проектирование ODOS](../superpowers/specs/2026-07-20-odos-orchestration-spec-design.md)

## Контекст

Проектирование ODOS определяет полный замкнутый словарь оркестрации, матрицу возможностей
для двух целевых платформ, политику отказов, границу компилятора и модель conformance из
шести групп. Если оставить это лишь проектным документом, conformance перестаёт быть
машиночитаемым, а оркестрации Dagster и Prefect могут дрейфовать независимо друг от друга.

ODOS — оркестрационный «сиблинг» ODTS под зонтиком **YADPS**. ODTS описывает, что вычисляет
трансформация; ODOS описывает, когда выполняется работа, в каком порядке и как она переживает
отказ. Ни один из стандартов не встраивает другой.

ADR-0016, напротив, фиксирует политику ODTS, но не содержит полной грамматики заголовков.
Поэтому два стандарта готовы к извлечению на разных уровнях.

## Решение

Принять [нормативный профиль ODOS 0.1](../../spec/ODOS/README.md) с:

- нормативной семантикой и требованиями conformance в `spec/ODOS/SPEC.md`;
- JSON Schema стандарта Draft 2020-12 с замкнутым словарём ключей;
- общими дефолтами и примерами шести групп, покрывающими полную проектную модель;
- детерминированными тестами на валидность схемы, покрытие групп, локальные ссылки, отклонение
  неизвестных ключей и явное ограничение целевой платформы для непереносимых хуков.

Каталог `spec/ODOS/` с заглавными буквами описывает стандарт. Будущий каталог со строчными
буквами `spec/orchestration/` содержит живые conforming-документы OGIP и остаётся входом для
планируемых адаптеров Dagster и Prefect. Примеры внутри пакета стандарта — это conformance-
фикстуры, а не второй рантайм-SSoT.

Документы ODOS используют семантику YAML 1.2. Ключ `"on"` в переносимых примерах заключён в
кавычки, потому что иначе YAML 1.1-совместимые загрузчики приводят его к булеву `true` до
валидации схемой.

Валидация схемой покрывает форму сериализации. Компилятор остаётся ответственным за
семантические проверки, которые JSON Schema выполнить не может: поиск в реестре, выбор по
графу ассетов, кросс-документные ссылки, совместимость партиций, возможности целевой
платформы и эквивалентность адаптеров.

Не публикуйте полный `spec/ODTS/0.1` только на основе ADR-0016. `spec/ODTS/README.md`
фиксирует отсутствующие поверхности грамматики до тех пор, пока управляющий документ их не
определит.

## Последствия

- У ODOS 0.1 теперь есть проверяемый и машинно-валидируемый контракт, независимый от любого из оркестраторов.
- Неизвестные ключи расширений отклоняются до проекции, сохраняя гарантию переносимости.
- Пример из шести групп становится приёмочной фикстурой для будущего компилятора.
- Живые документы ODOS и адаптеры по-прежнему остаются работой по реализации; это решение не
  утверждает, что вывод для Dagster или Prefect уже генерируется.
- Извлечение ODTS остаётся честным: политика принята, но conformance нельзя заявлять, пока не
  существуют полная грамматика и отображение в IR.
