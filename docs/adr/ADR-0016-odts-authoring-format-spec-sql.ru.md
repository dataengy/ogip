# ADR-0016 — Формат авторства `@odts` для `spec/sql`: компактный заголовок, макросы, дисциплина SQL

- **Status:** Accepted
- **Date:** 2026-07-20
- **Relates to:** D0/D5 · [ADR-0005](ADR-0005-spec-ssot-bruin-odcs-compiler.md) · [ADR-0004](ADR-0004-sqlmesh-default-transform-engine.md) · [ADR-0001](ADR-0001-edw-layering-no-medallion.md)

## Context

[ADR-0005](ADR-0005-spec-ssot-bruin-odcs-compiler.md) сделал `spec/` источником истины (SSoT) и
зафиксировал формат авторства как **Bruin asset** (`/* @bruin <yaml> @bruin */` + SQL). Против
него накопились три давления:

1. **Многословность.** `spec/sql/core/game.sql` тратит 16 строк заголовка на метаданные для
   12-строчной модели. Заголовок — та часть, которую агенты правят чаще всего, а вложенный YAML
   стоит токенов, провоцирует ошибки отступов и порождает шумные diff при изменении одного
   атрибута.
2. **Имя вендора внутри вендоро-нейтрального SSoT.** `@bruin` помечает SSoT именем одной из шести
   целей — ровно та связанность, ради предотвращения которой существует ADR-0005. Bruin здесь —
   *сериализация* авторства, никогда не продакшн-зависимость, но маркер читается иначе.
3. **Нет слоя макросов.** Суррогатный ключ написан вручную (`md5(cast(game_id as varchar))`).
   У движка по умолчанию, SQLMesh, есть нативные `@`-макросы; эта выразительность не используется.

Также нет письменной политики о том, что вообще может *войти* в формат, поэтому каждое
предложение — альтернативные синтаксисы SQL, поблочное версионирование, семантические атрибуты —
пересуждается с нуля.

## Decision

Ввести **`@odts 0.1`**, компактный строчно-ориентированный заголовок для `spec/sql`, и зафиксировать
политику, управляющую его эволюцией.

`@odts` — это **реализация** OGIP стандарта **ODTS** (Open Data Transformation Standard), который
лежит под зонтиком **YADPS** (Yet Another Data Platform Standard) рядом с **ODOS** (Open Data
Orchestration Standard). OGIP соответствует стандарту; он не является его автором. Это разделение
несущее: то, что ODOS владеет оркестрацией, — ровно причина, по которой Prefect и Dagster **не**
являются целями компиляции ODTS в этом репозитории, а являются потребителями скомпилированных
проектов.

### Почему зонтик — `YADPS`, а не `ODPS`

`ODPS` занят дважды, в собственной экосистеме OGIP: Bitol'овским
[Open Data Product Standard](https://bitol-io.github.io/open-data-product-standard/v1.0.0/) и
[Open Data Product Specification](https://opendataproducts.org/) от Linux Foundation. Bitol
также сопровождает **ODCS**, который `spec/contracts/` уже использует — так что читатель, видящий
ODCS и ODPS бок о бок здесь, разумно заключил бы, что оба — от Bitol, и ошибся бы. Путаница
задокументирована в первоисточнике, а не гипотетична: ODPI публикует
[разъяснение ODPS vs ODCS](https://blog.opendataproducts.org/when-standards-collide-clarifying-odps-and-odcs-in-the-data-product-landscape-c2978f9c13d9)
именно потому, что люди их смешивают.

**Конвенция: имя, которое сталкивается, берёт `YA` (Yet Another) вместо `Open`.** Самоирония
здесь точна, а не декоративна — она говорит, что этот зонтик не претендует быть *тем самым*
платформенным стандартом, что есть та же позиция, что и не-цели ниже.

`ODTS` и `ODOS` были проверены и незаняты, поэтому они сохраняют форму `Open`. Семейство
намеренно асимметрично: только имя, наступившее на занятую землю, несёт маркер.

**Компиляция вынесена вперёд, а не переписана.** Фронтенд в `src/ogip/spec_compile/` отрисовывает
`@odts` в существующий YAML-заголовок `@bruin`; `parse_asset()` и каждый адаптер
(`to_sqlmesh` · `to_dbt` · `to_bruin` · `to_sqlmesh_dbt`) остаются неизменными.

```
spec/sql/**/*.sql  (@odts, SSoT)  ──▶  rendered @bruin YAML  ──▶  parse_asset() ──▶ adapters
```

Отрисованный YAML **никогда не коммитится** — одна копия, без дрейфа. `@bruin` остаётся читаемым
во время миграции; фронтенд диспетчеризует по маркеру.

Политика, в силе с этой записи:

| Rule | Decision |
|---|---|
| **Format versioning** | Одна версия на файл (`@odts 0.1`). Без поблочных версий — они покупают независимую эволюцию ценой матрицы совместимости, которую пришлось бы тестировать. |
| **Macros** | Разрешены как `@ns.name(args)`, определяются один раз в реестре, компилируются **нативно под каждый движок** (SQLMesh `@DEF` · dbt/Bruin Jinja · plain-SQL раскрытие). Расходящиеся реализации одной семантики защищены тестами конформности (ниже). |
| **Jinja in `spec/`** | Запрещён. Jinja может появляться только в *сгенерированных* проектах. |
| **LValue projections** | Разрешены только через `:=` (`sk := md5(id)`), десугарятся фронтендом. Никогда `=`. |
| **Pipe syntax** | Отложено до `@odts 0.2`; не отклонено. |
| **Vendor terms** | Запрещены в `spec/` (`MergeTree`, `Delta`, `Iceberg`, имена движков). Специфика движков живёт только в `spec/sql/_ext/<engine>/`. |
| **Formatter** | Существующая конфигурация **sqlfluff** (`pyproject.toml [tool.sqlfluff]`) канонична. Никакого второго форматтера. |
| **Compile targets** | Шесть реальных: `sqlmesh` · `dbt` · `opendbt` · `sqlmesh-dbt` · `bruin` · plain-SQL runner. Оркестраторы **не** являются целями компиляции — они потребляют скомпилированные проекты. |

### Почему `=` запрещён, а `:=` нет

Оба парсятся. Они не означают одно и то же, и только один падает громко — проверено на версиях,
закреплённых в этом репозитории (sqlglot 30.8.0, DuckDB 1.5.4, sqlfluff 4.2.2):

| Written | sqlglot node | DuckDB |
|---|---|---|
| `select name = title` | `EQ` — предикат **равенства**, дающий булев столбец | выполняется, молча неверно |
| `select name := title` | `PropertyEQ` — отдельный узел | `Parser Error`, падает громко |
| `list_value(a := 1)` | именованный аргумент, вложенный | выполняется корректно |

`=` — опасный класс синтаксиса: валиден, исполним и тихо не то, что имел в виду автор.
`:=` однозначен для парсера и отвергается движком, поэтому не может достичь продакшна
нераскрытым. Фронтенд десугарит `PropertyEQ` **только как прямого потомка списка проекции** —
вложенный `:=` остаётся именованным аргументом DuckDB.

### Почему pipe-синтаксис отложен, а не отклонён

`|>` — синтаксис BigQuery, не DuckDB. DuckDB 1.5.4 отвергает его, а sqlfluff 4.2.2 не может его
распарсить — так что сегодня его нельзя написать. Но sqlglot десугарит его корректно в CTE с
сохранённым происхождением, что означает, что тот же фронтенд, который раскрывает заголовки
`@odts`, может раскрыть pipe прежде, чем любой из инструментов его увидит. Это расширение `0.2`
с известным путём реализации.

### Конформность макросов

Компиляция одного макроса в четыре нативные реализации — это четыре шанса разойтись, и реалистичный
провал молчалив: `dbt_utils.generate_surrogate_key` не даёт того же хеша, что
`md5(cast(x as varchar))`, поэтому одна и та же модель ключевалась бы по-разному на разных профилях
запуска. Поэтому каждый макрос несёт **тест конформности**: одна фикстура, прогнанная через каждый
адаптер на DuckDB, утверждающая побайтово идентичный вывод. Расхождение — CI-красное, а не инцидент
данных, обнаруженный ниже по потоку.

## Consequences

- Заголовки сжимаются примерно вдвое; diff становятся строчно-ориентированными и правимыми агентом.
- SSoT больше не несёт имени цели.
- `spec/` по-прежнему читается без какого-либо **движкового** бинарника (инвариант ADR-0005);
  теперь ему нужен собственный фронтенд-парсер OGIP, который является простым Python в этом
  репозитории — не движковая зависимость.
- Мы владеем парсером и реестром макросов. Это реальная поверхность сопровождения, принятая,
  потому что альтернатива (ручные вендорские макросы на движок) имеет худший режим отказа.
- Два формата заголовка сосуществуют во время миграции; фронтенд должен диспетчеризовать по
  маркеру, пока последний файл `@bruin` не будет сконвертирован.

## Alternatives considered

- **Оставить YAML `@bruin` без изменений** — нулевая стоимость, но оставляет многословность и
  вендорский маркер в SSoT, и никогда не получает слоя макросов.
- **Компилировать `@odts` прямо в датакласс `Asset`**, минуя YAML — тоньше, но
  `to_bruin` копирует файлы дословно и всё равно нуждался бы в реальном тексте `@bruin`.
  Промежуточная отрисовка требуется существующей целью, поэтому её сокрытие ничего не покупает.
- **Раскрывать макросы в нативный SQL для всех целей, включая SQLMesh** — один путь исполнения и
  нет риска дрейфа, но отбрасывает нативные `@`-макросы SQLMesh, возможность продакшн-движка.
  Отклонено в пользу нативного маппинга плюс тестов конформности.
- **Поблочные версии грамматики** (`columns(0.2 patch infer:sql)`) — независимая эволюция ценой
  матрицы совместимости версий. Отклонено как сложность без точки вызова.
- **Авторство стандарта вместо его реализации** — вести сам ODTS из этого репозитория вне области
  по [AGENTS.md](../../AGENTS.md): полярная звезда — продакшн-платформа, *а не* «следующий dbt».
  OGIP вносит соответствующую реализацию; амбиция `@odts` внутри репозитория — переносимость через
  шесть целей OGIP, и предложения синтаксиса судятся против них, а не против воображаемой индустрии.
